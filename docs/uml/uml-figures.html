Software Engineering — UML Deliverables

Seven diagrams, traced to the shipped codebase

Every figure below was checked against the actual source of Rise, Tarnished — not drawn from a template and relabeled. The plan this was built from (docs/uml-plan.md) went through two rigor passes and caught six real modeling errors before a single diagram was drawn; three more were caught while drawing. Every correction is left visible below rather than silently fixed, because the corrections are evidence of rigor, not a flaw to hide.

Corrected
  • Include vs. extend. Dodge, Block, and Cast Sorcery were first modeled as «include» of Fight the Adaptive Boss. All three are player choices, not guaranteed steps — moved to «extend». Move and Attack stayed «include» because winning is provably impossible without them.
  • A fabricated relationship. The first class-diagram draft claimed BossCombatState depends on PlayerBuild. Checked BossStepContext directly — it has no build field at all. Dropped entirely rather than patched.
  • A backwards, invalid dependency. Boss ↔ AttemptLog was drawn with the arrow pointing the wrong way and carrying an association-style multiplicity on a dependency arrow, which UML doesn't permit. Rebuilt as a correctly-directed, stereotyped association instead.
Modeling call
  • The system is a functional core / imperative shell (ADR-0001) — state lives in plain interfaces, transformed by pure functions, not classes with instance methods. The class diagram models each state interface as a class with its real fields and its real pure functions as operations, rather than inventing OOP methods that don't exist in the source.
  • Mermaid has no native use-case or communication diagram syntax. Both are built with flowchart — stadium shapes standing in for UML ovals, and numbered edge labels standing in for a communication diagram's message sequence. Noted at each figure, not hidden.

Figure 02 · Detailed Use Case Description

UC-05 — Fight the Adaptive Boss

Chosen as the one detailed description because it's the only use case with real alternate flows, a real failure path, and real business rules — everything else is infrastructure or a single RPC call.

Primary ActorPlayer
PreconditionsSigned in, on /play; fight:start fired with a real PlayerBuild — CombatScene.startFight() has run and this.ready === true.
Postconditions — windetermineFightOutcome returns 'victory'; fight:outcome emitted with an optimistic estimate; Resolve Attempt persists the real reward.
Postconditions — lossSame event, result: 'death'; reward computed as 0 by design — death pays nothing, enforced again server-side and never trusted from the client.
TriggerThe fight:start bridge event, once PlayShell has a resolved build.
Main flowFixed 60Hz tick: sample input → playerCombat.step → bossCombat.step (L2 tactic re-score, L3 move selection) → cross-entity hit resolution → render → repeat until a terminal HP state.
Alt flowsA1 Dodge (i-frames) · A2 Block (stamina drain, guard break) · A3 Cast Sorcery (FP-gated) · A4 Boss PUNISH pre-empts on an opening · A5 Boss RECOVER skips selection entirely · A6 Posture break opens a critical window.
ExceptionsE1 Simultaneous near-KO resolves to exactly one outcome, never double-reported · E2 A stalled frame is capped at 5 ticks' catch-up, never a runaway burst.
Business rulesF1 tell ≥18 ticks · F2 ≥30-tick sequence gap · F3 chain cap · F5 punish ≤1/4s · F7 grabs never combo · F8 no 3rd consecutive repeat.

Fight the Adaptive Boss — one tick, a light attack connects

Scope is deliberately one representative tick, not the whole multi-minute fight — showing "loop 3,600+ times" end to end would communicate less than one real tick does.

CombatScene.ts (update, resolvePlayerAttackOnBoss) playerCombat.ts (step) bossCombat.ts (step, resolveBossHit) tactics.ts (tickTactic) actionSelection.ts (selectTopLevel) 
sequenceDiagram
    actor Player
    participant Scene as CombatScene
    participant PC as playerCombat<br/>(pure)
    participant BC as bossCombat<br/>(pure)
    participant Tac as TacticMachine<br/>(tactics.ts)
    participant Sel as ActionSelection<br/>(actionSelection.ts)

    loop every 60Hz tick, until determineFightOutcome() != null
        Player->>Scene: keyboard input this frame
        Scene->>Scene: sampleInput() → CombatInput

        Scene->>PC: step(sim, input, ctx)
        PC-->>Scene: {state, events: [attack:active]}

        alt attack:active event (light attack)
            Scene->>Scene: resolvePlayerAttackOnBoss('light')
            Scene->>Scene: meleeDamage('light', build.dexterity)
            Scene->>BC: resolveBossHit(boss, {hp, poise, postureDamage})
            BC-->>Scene: {state, wasCritical}
            Scene->>Scene: triggerHitstop() / shake() / sfx('hit')
        end

        Scene->>BC: step(boss, bossCtx)
        BC->>Tac: tickTactic(prev, getSignals, ctx)
        Note over Tac: runs unconditionally every tick —<br/>even mid-swing or staggered
        Tac-->>BC: {state, changed}

        alt boss idle (action == null) and tactic != RECOVER
            BC->>Sel: selectTopLevel(table, ids, distance, state, weighting)
            Sel-->>BC: {kind:'move', moveId} or {kind:'no-action'}
        else tactic == RECOVER
            Note over BC: selection skipped —<br/>approach() only
        end
        BC-->>Scene: {state, events}

        Scene->>Scene: determineFightOutcome(boss.hp, sim.hp)
        Scene->>Scene: render() — sprites, HUD, audio
    end

    Scene-->>Player: outcome reached → fight:outcome emitted
No network round-trip happens during the fight — step() is pure, local state only, which is what makes the fixed-timestep loop replayable from a seed.
The RECOVER branch is drawn explicitly — it's the exact mechanism a prior playtest fix (PR #48) added, so the boss now gives a smothered player real relief instead of escalating pressure.

Spend Runes on Stats

Chosen for the communication (not sequence) treatment because its story is about which object owns which piece of validation — the RPC vs. the row it locks — which a hub-and-spoke layout foregrounds better than a timeline. Mermaid has no native communication-diagram type; this is built with numbered, labelled flowchart edges.

src/components/CharacterSheet.tsx (confirmSpend) …spend_stat_point.sql 
flowchart TD
    Player(["Player"])
    Sheet[":CharacterSheet"]
    Client[":SupabaseClient"]
    PostgREST[":PostgREST"]
    RPC[":spend_stat_point()<br/>«SECURITY DEFINER»"]
    Table[("player_stats<br/>(row, locked)")]

    Player -- "1: click '+1'<br/>(already armed)" --> Sheet
    Sheet -- "2: rpc('spend_stat_point',<br/>{p_stat})" --> Client
    Client -- "3: HTTPS request + JWT" --> PostgREST
    PostgREST -- "4: invoke as<br/>authenticated role" --> RPC
    RPC -- "5: SELECT ... FOR UPDATE" --> Table
    Table -- "6: locked row value" --> RPC
    RPC -- "7: cost = 100+25×(current-10);<br/>UPDATE ... WHERE runes>=cost<br/>AND current<60" --> Table
    Table -- "8: RETURNING new row,<br/>or 0 rows affected" --> RPC
    RPC -- "9: new stats/runes,<br/>or raise exception" --> PostgREST
    PostgREST -- "10: JSON response" --> Client
    Client -- "11: {data, error}" --> Sheet
    Sheet -- "12: re-render<br/>updated stat sheet" --> Player
Message 5 is the whole point of this diagram. The next point's cost depends on the stat's current value, so it must be read before it's charged for. A plain SELECT first would let two concurrent calls both read the same pre-spend value and both pass a balance check against runes neither has actually paid — SELECT ... FOR UPDATE closes that race.
The client never supplies an amount (ADR-0003) — p_stat selects which rule applies; the RPC computes cost and validates the hard cap itself, server-side, every time.

Boss L2→L3 Decision Process (one tick)

The named criterion was "whose decision-making is best understood as a workflow" — nothing else in the system comes close on decision density. Two structural facts, re-verified against source before drawing: L2 runs every tick unconditionally, and RECOVER skips L3 entirely rather than biasing it.

    end

    Gate2 -- no --> Gate3{action == null<br/>boss idle?}

        ComboResult -- no --> SeqEnd1[sequence-end, start F2 gap]

        Gate3 -- yes, idle --> RecoverCheck{tactic == RECOVER?}

        GapCheck -- no --> EligFilter[Filter table: range, cooldown, F8]

        EligEmpty -- no --> TacticMatch{Any move tags match<br/>current tactic?}

        TacticMatch -- no --> PoolFallback["pool = full eligible set<br/>(documented fallback)"]

    SeqEnd2 --> End
    ApproachOnly --> End

Notation caveat, stated on purpose: standard UML decision nodes carry mutually-exclusive boolean guards. The two weighted picks here are probabilistic — nothing about system state alone determines the branch, only a distribution does. Both are labelled {probabilistic} rather than drawn like an ordinary if.

AttemptLog → Boss — corrected twice over. First draft had the dependency arrow pointing the wrong way (a dependency points from the dependent to what it depends on) and carrying an association-style multiplicity, which a dependency can't. Checked the schema directly: no FK exists — attempt_logs.boss_id is validated only inside resolve_attempt, never by Postgres. Rebuilt as a correctly-directed association, stereotyped to say so.
AuthUser — PlayerStats/PlayerProgress are 0..1, not 1 — provisioning is an application-level trigger, not a schema guarantee. A backfill migration exists precisely because pre-trigger accounts once had zero.
