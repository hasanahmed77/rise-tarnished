Software Engineering, UML Deliverables

Seven diagrams for Rise, Tarnished

Rise, Tarnished is a 2D souls-like boss-rush game. Each diagram below is traced directly to the shipped source code (docs/uml-plan.md documents the full modeling plan).

Figure 01 · Use Case Diagram

The shipped MVP loop

Player, Google, and Supabase are the actors. The diagram covers the loop that is actually implemented, sign in, resume, fight, view outcome, and resolve or spend runes.

src/app/page.tsx src/app/play/page.tsx src/app/auth/callback/route.ts src/components/CharacterSheet.tsx src/game/scenes/CombatScene.ts
A sub-behavior is «include»d only if it is performed, unconditionally, at a defined point in every completed instance of the base use case, not merely because it can happen.
Supabase is modeled as a secondary actor rather than inside the system boundary. The use cases describe player goals, and Supabase is a service the system calls out to, not something the player interacts with directly.

Figure 02 · Detailed Use Case Description

UC-05, Fight the Adaptive Boss

This use case is documented in detail because it has real alternate flows, a real failure path, and real business rules. The remaining use cases are simple infrastructure or a single RPC call.

src/game/scenes/CombatScene.ts src/game/combat/playerCombat.ts src/game/boss/bossCombat.ts src/game/attempt/outcome.ts docs/design/BOSS_AI.md
Primary ActorPlayer
PreconditionsSigned in and on /play. fight:start fired with a real PlayerBuild. CombatScene.startFight() has run and this.ready is true.
Postconditions, windetermineFightOutcome returns 'victory'. fight:outcome is emitted with an optimistic estimate. Resolve Attempt persists the real reward.
Postconditions, lossSame event, with result: 'death'. Reward is computed as 0 by design. Death pays nothing, and this is enforced again server-side rather than trusted from the client.
TriggerThe fight:start bridge event, once PlayShell has a resolved build.
Main flowFixed 60Hz tick. Sample input, then playerCombat.step, then bossCombat.step (L2 tactic re-score, L3 move selection), then cross-entity hit resolution, then render. Repeats until a terminal HP state.
Alt flowsA1 Dodge (i-frames) · A2 Block (stamina drain, guard break) · A3 Cast Sorcery (FP-gated) · A4 Boss PUNISH pre-empts on an opening · A5 Boss RECOVER skips selection entirely · A6 Posture break opens a critical window.
ExceptionsE1 Simultaneous near-KO resolves to exactly one outcome, never double-reported · E2 A stalled frame is capped at 5 ticks' catch-up, never a runaway burst.
Business rulesF1 tell ≥18 ticks · F2 ≥30-tick sequence gap · F3 chain cap · F5 punish ≤1/4s · F7 grabs never combo · F8 no 3rd consecutive repeat.

Sign In (with Google)

A strictly time-ordered four-hop redirect chain, shown as a vertical timeline. The provisioning step is wrapped in an opt fragment because it only fires the first time a given Google account signs in.

No password ever touches this system. Google OAuth is the sole sign-in method (ADR-0003).
PlayPage is a server component. auth.getUser() runs on the server before any HTML reaches the browser.

Figure 04 · Sequence Diagram (Member B)

Fight the Adaptive Boss (One Tick, Light Attack Connects)

Scope is deliberately one representative tick rather than the whole multi-minute fight. Showing the loop repeat 3,600+ times end to end would communicate less than one real tick does.

CombatScene.ts (update, resolvePlayerAttackOnBoss) playerCombat.ts (step) bossCombat.ts (step, resolveBossHit) tactics.ts (tickTactic) actionSelection.ts (selectTopLevel) 
sequenceDiagram
    actor Player
    participant Scene as CombatScene
    participant PC as playerCombat<br/>(pure)
    participant BC as bossCombat<br/>(pure)
    participant Tac as TacticMachine<br/>(tactics.ts)
    participant Sel as ActionSelection<br/>(actionSelection.ts)

    loop every 60Hz tick, until determineFightOutcome() != null
        Player->>Scene: keyboard input this frame
        Scene->>Scene: sampleInput() → CombatInput

        Scene->>PC: step(sim, input, ctx)
        PC-->>Scene: {state, events: [attack:active]}

        alt attack:active event (light attack)
            Scene->>Scene: resolvePlayerAttackOnBoss('light')
            Scene->>Scene: meleeDamage('light', build.dexterity)
            Scene->>BC: resolveBossHit(boss, {hp, poise, postureDamage})
            BC-->>Scene: {state, wasCritical}
            Scene->>Scene: triggerHitstop() / shake() / sfx('hit')
        end

        Scene->>BC: step(boss, bossCtx)
        BC->>Tac: tickTactic(prev, getSignals, ctx)
        Note over Tac: runs unconditionally every tick,<br/>even mid-swing or staggered
        Tac-->>BC: {state, changed}

        alt boss idle (action == null) and tactic != RECOVER
            BC->>Sel: selectTopLevel(table, ids, distance, state, weighting)
            Sel-->>BC: {kind:'move', moveId} or {kind:'no-action'}
        else tactic == RECOVER
            Note over BC: selection skipped,<br/>approach() only
        end
        BC-->>Scene: {state, events}

        Scene->>Scene: determineFightOutcome(boss.hp, sim.hp)
        Scene->>Scene: render() with sprites, HUD, audio
    end

    Scene-->>Player: outcome reached → fight:outcome emitted
No network round-trip happens during the fight. step() is a pure function over local state only, which is what makes the fixed-timestep loop replayable from a seed.
The RECOVER branch is drawn explicitly. It gives a smothered player real relief instead of escalating pressure further.

Figure 05 · Communication Diagram (Member C)

Spend Runes on Stats

Shown as a communication diagram rather than a sequence diagram because the story is about which object owns which piece of validation, the RPC versus the row it locks. Objects are linked in a chain, and the twelve messages are numbered in execution order along the link each one travels.

src/components/CharacterSheet.tsx (confirmSpend) …spend_stat_point.sql
Message 5 is the whole point of this diagram. The next point's cost depends on the stat's current value, so it must be read before it's charged for. A plain SELECT first would let two concurrent calls both read the same pre-spend value and both pass a balance check against runes neither has actually paid. SELECT ... FOR UPDATE closes that race.
The client never supplies an amount (ADR-0003). p_stat selects which rule applies, and the RPC computes cost and validates the hard cap itself, server-side, every time.

Figure 06a · Activity Diagram, Tactic Selection

Boss L2 Tactic Machine (one tick)

This diagram was chosen because the boss AI's decision-making is best understood as a workflow, and nothing else in the system has comparable decision density. L2 runs every tick unconditionally, before the stagger and posture gates, so intent can shift mid-swing. The action-selection half of the same tick continues in Figure 06b.

bossCombat.ts (step) tactics.ts (tickTactic) actionSelection.ts (selectTopLevel, selectComboBranch) 
flowchart TD
    Start(("●")) --> Decay("Passive per-tick decay of<br/>poise, posture, selection cooldowns")
    Decay --> L2Start

    subgraph L2["L2 Tactic Machine, runs every tick unconditionally"]
        direction TB
        L2Start{"Punishable opening<br/>AND cooldown == 0<br/>AND tactic != PUNISH?"}
        L2Start -- yes --> SetPunish("Set tactic = PUNISH<br/>reset F5 cooldown")
        L2Start -- no --> HoldCheck{"Hold timer expired?"}
        HoldCheck -- no --> KeepTactic("Keep current tactic")
        HoldCheck -- yes --> Softmax("Softmax pick over 5 tactics<br/>probabilistic, weights =<br/>BASE_SCORE × behaviorMod")
        Softmax --> NewTactic("New tactic + new hold duration")
    end

    SetPunish --> Gate1
    KeepTactic --> Gate1
    NewTactic --> Gate1

    Gate1{"staggerTicks > 0?"}
    Gate1 -- yes --> WaitStagger("Decrement stagger, no action")
    Gate1 -- no --> Gate2{"Posture critical window open?"}
    Gate2 -- yes --> Frozen("Collapsed, frozen")
    Gate2 -- no --> Gate3{"action == null, boss idle?"}
    Gate3 --> L3Ref["Continue to L3 Action Selection<br/>see Figure 06b"]

    WaitStagger --> End(("●"))
    Frozen --> End
Standard UML decision nodes carry mutually-exclusive boolean guards. The softmax pick is probabilistic, since nothing about system state alone determines the branch, only a distribution does. It is labeled probabilistic rather than drawn like an ordinary if.
The tactic machine sits before the stagger and posture gates, so the boss can change intent while it is mid-swing or staggered. Only the resulting action waits on the animation.

    SeqEnd2 --> End

    ApproachOnly2 --> End
    ApproachOnly3 --> End
    StartMove2 --> End
When the active tactic is RECOVER, selection is skipped outright rather than run with a biased weighting. This is the one path that guarantees a smothered player a tick of relief.
If no eligible move carries a tag matching the current tactic, the pool falls back to the full eligible set rather than stalling. The fallback is a documented rule, not an accident.

In-Memory State for Combat, Boss AI, and the Scene

GameBridge and CombatScene are the two real OOP classes and are drawn as themselves. This diagram covers domain and runtime state. Persistence classes are shown separately in Figure 07b.

AttemptLog references Boss through boss_id, but no foreign key exists at the database level. The value is validated only inside resolve_attempt, not by Postgres, so the relationship is stereotyped «not FK-enforced».
AuthUser to PlayerStats and PlayerProgress are 0..1 relationships, not 1, since provisioning happens through an application-level trigger rather than a schema guarantee. A backfill migration exists because pre-trigger accounts once had zero.
